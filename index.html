cert-manager + Venafi — Certificate Lifecycle Use Cases

Context

The platform uses:

  • OpenShift
  • cert-manager
  • Venafi Self-Hosted (TPP)
  • Venafi-backed Issuer or ClusterIssuer

The objective is to understand what the native cert-manager + Venafi integration can do, and where a custom external issuer would be required.

Basic Use Case — New Namespace, New Route, New Certificate

Situation

A user creates a new OpenShift namespace and deploys a new Route:

Namespace: team-a

Route: app.example.com

There is no existing Kubernetes Certificate, no TLS Secret, and no existing certificate for this DNS name in Venafi.

The user creates a cert-manager Certificate:

apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: app-cert
  namespace: team-a
spec:
  secretName: app-tls
  dnsNames:
    - app.example.com
  issuerRef:
    name: venafi-issuer
    kind: Issuer

Native cert-manager flow

The flow is:

Certificate
    ↓
cert-manager creates CertificateRequest
    ↓
Venafi Issuer
    ↓
Venafi TPP
    ↓
certificate is issued
    ↓
cert-manager stores it in Secret

Venafi is responsible for issuing the certificate. cert-manager manages the Kubernetes-side certificate lifecycle.

What cert-manager generates

Before asking Venafi for the certificate, cert-manager generates a private key and CSR.

Conceptually:

cert-manager
    │
    ├── Private key
    │       ↓
    │   kept in Kubernetes Secret
    │
    └── CSR
            ↓
       CertificateRequest
            ↓
          Venafi

The CSR contains the requested identity, for example:

DNS SAN:
    app.example.com

Venafi signs the CSR and returns the certificate.

At the end, cert-manager creates/updates the TLS Secret:

Secret: app-tls

tls.crt
    ↓
certificate issued by Venafi

tls.key
    ↓
private key generated by cert-manager

The important point is:

cert-manager generates the private key and CSR; Venafi signs/returns the certificate.

The final Kubernetes state is:

Namespace
   │
   ├── Route: app.example.com
   │
   ├── Certificate: app-cert
   │
   └── Secret: app-tls
          ├── tls.crt
          └── tls.key

The Route uses the resulting TLS Secret.

Use Case 1 — New Route, but the certificate already exists in Venafi

Situation

A user creates:

Namespace
  ├── Route: app.example.com
  ├── Certificate
  └── Secret

Before this, a valid certificate for:

app.example.com

already exists in Venafi.

The user wants cert-manager to discover that certificate and use it instead of creating another certificate.

Native cert-manager solution

If the existing certificate and private key are already available in the Kubernetes Secret

This is supported.

The existing TLS Secret can be used as the target Secret of the Certificate.

Example:

apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: app-cert
spec:
  secretName: app-tls
  dnsNames:
    - app.example.com
  issuerRef:
    name: venafi-issuer
    kind: Issuer

If the Secret already contains a valid certificate and matching private key, cert-manager can use that existing Secret as the current certificate state.

The important persistence object is therefore the Kubernetes Secret.

If the certificate exists only in Venafi

Example:

Venafi:
  app.example.com → certificate exists

OpenShift:
  no Certificate
  no Secret

Native cert-manager does not perform a Venafi inventory lookup by DNS name before issuance.

The normal flow is:

Certificate
    ↓
CertificateRequest
    ↓
Venafi Issuer
    ↓
Venafi issues certificate

Therefore, if the certificate exists only in Venafi, native cert-manager can request another certificate.

Native conclusion

Existing state Native behavior
Valid certificate + matching key in Kubernetes Secret Reuse existing Secret state
Certificate exists only in Venafi No automatic Venafi lookup/adoption
No Secret and no Certificate New issuance

cert-manager’s Certificate resource manages the target Secret and uses the Secret/certificate state for its lifecycle. It does not provide a generic Venafi certificate-inventory lookup before issuance.

Use Case 2 — User deletes the namespace and recreates everything

Situation

Initially:

Namespace: team-a

Route
  ↓
Certificate
  ↓
Secret
  ↓
Venafi certificate

The user deletes the entire namespace:

Namespace ❌
  ├── Route ❌
  ├── Certificate ❌
  └── Secret ❌

The Venafi certificate still exists and is valid.

Later, the user recreates the namespace and creates everything from scratch:

New Namespace
  ├── Route
  ├── Certificate
  └── Secret

Native cert-manager solution

If the Secret was backed up and restored

Restore the TLS Secret first, then recreate the Certificate.

Backup
  ↓
Restore Secret
  ↓
Create Certificate
  ↓
cert-manager sees existing certificate state

This avoids unnecessary issuance.

If the Secret was permanently deleted

Native cert-manager cannot recover the certificate from Venafi simply because the same DNS name exists there.

The new Certificate has no target Secret containing the previous certificate/private key.

The normal behavior is:

New Certificate
      ↓
No existing Secret
      ↓
CertificateRequest
      ↓
Venafi Issuer
      ↓
New certificate request

Therefore:

Deleting the Secret means cert-manager loses the Kubernetes-side certificate state. A valid certificate remaining in Venafi is not automatically discovered by native cert-manager.

cert-manager documents that deleting a Secret associated with a Certificate triggers reissuance; preserving/restoring the Secret is the native way to preserve the existing certificate state.

Native recommendation

If namespace deletion/recreation is expected:

Keep/backup TLS Secrets
        ↓
Restore Secrets
        ↓
Restore/Create Certificates

The Secret must be treated as persistent certificate state.

Use Case 3 — Production: two new clusters, two new Routes, same URL, no certificate in Venafi

Situation

There are two new production clusters:

Cluster 1
  └── Route: app.example.com

Cluster 2
  └── Route: app.example.com

There is currently no certificate for app.example.com in Venafi.

Each cluster has cert-manager and its own Venafi issuer.

If both clusters independently create a Certificate:

Cluster 1
  Certificate
      ↓
  Venafi
      ↓
  Certificate #1

Cluster 2
  Certificate
      ↓
  Venafi
      ↓
  Certificate #2

Native cert-manager does not provide a cross-cluster coordination mechanism that says:

“Another cluster is already requesting this DNS identity, so use the same certificate.”

Native solution

If the requirement is one certificate shared by both clusters, choose one cluster as the certificate owner:

                 Venafi
                   │
                   ▼
              Cluster 1
              cert-manager
                   │
              Certificate
                   │
                Secret
                   │
          Secret replication
                   │
                   ▼
              Cluster 2
                 Secret

Then:

Cluster 1 Route ──> Secret
Cluster 2 Route ──> Secret

Only Cluster 1 performs the Venafi issuance/renewal.

Cluster 2 receives the resulting Secret through the organization’s approved Secret replication mechanism.

This avoids two independent Venafi issuance requests.

Important

Native cert-manager does not coordinate the two clusters itself.

If both clusters independently use their own Issuer/ClusterIssuer for the same DNS name, they can request separate certificates.

Native cert-manager + Venafi summary

Use case Native solution Result
Certificate already in Venafi + certificate/key already in Kubernetes Secret Create Certificate pointing to existing Secret Existing Kubernetes certificate state can be used
Certificate only in Venafi, no Kubernetes Secret Normal Certificate → CertificateRequest → Venafi New certificate can be requested
Namespace deleted + Secret backed up/restored Restore Secret before Certificate Avoid unnecessary issuance
Namespace deleted + Secret permanently deleted Recreate Certificate New Venafi request
Two clusters, same URL, no existing certificate One cluster owns Certificate + replicate Secret One Venafi issuance
Two clusters independently request same URL Two independent CertificateRequests Potentially two Venafi certificates

Custom External Issuer Solution

If the requirement is:

“Before issuing, check Venafi to see whether a valid certificate already exists for the requested DNS identity.”

Then a custom external issuer can implement this behavior.

cert-manager officially supports external issuers. An external issuer watches CertificateRequest resources whose issuerRef points to the external issuer and returns the signed certificate through the CertificateRequest status.

Custom flow

Certificate
     ↓
cert-manager
     ↓
CertificateRequest
     ↓
Custom Venafi External Issuer
     ↓
Extract DNS SAN
     ↓
Search Venafi
     │
     ├── Existing valid certificate
     │
     │       ↓
     │   reuse/adopt according to policy
     │
     └── No certificate
             ↓
         request new
             ↓
           Venafi

Existing certificate path

For:

app.example.com

the custom issuer can query Venafi for certificates matching the DNS SAN.

It then validates the candidate according to defined rules:

DNS SAN matches
       +
certificate is valid
       +
correct Venafi policy/zone
       +
correct ownership
       +
private key can safely be reused

Only then should it return the existing certificate.

New certificate path

If no usable certificate exists:

CertificateRequest
      ↓
Custom External Issuer
      ↓
Venafi enrollment
      ↓
New certificate
      ↓
CertificateRequest Ready=True
      ↓
cert-manager writes Secret

Important private-key constraint

A certificate cannot safely be reused with an unrelated private key.

If:

Venafi:
  app.example.com
  certificate A

but cert-manager creates:

new private key B
new CSR B

then certificate A cannot simply be placed into the TLS Secret because certificate A does not match private key B.

Therefore, if the Kubernetes Secret was deleted, a custom issuer must have a defined private-key strategy.

Possible requirement:

Existing Venafi certificate
        +
matching private key
        ↓
safe reuse

If the matching private key is unavailable, the issuer should not blindly reuse the certificate.

Custom External Issuer Architecture

                     OpenShift
                         │
                    Certificate
                         │
                         ▼
                 CertificateRequest
                         │
                         ▼
              ┌──────────────────────┐
              │ Custom Venafi Issuer  │
              │                      │
              │ 1. Read CSR          │
              │ 2. Extract DNS SAN   │
              │ 3. Query Venafi      │
              │ 4. Validate match    │
              │ 5. Reuse or issue    │
              └──────────┬───────────┘
                         │
                         ▼
                    Venafi TPP

The custom issuer remains outside cert-manager core.

cert-manager continues to manage:

Certificate
CertificateRequest
Secret
Renewal lifecycle

The custom issuer manages:

Venafi lookup
Venafi certificate identity
Reuse/adoption policy
Venafi issuance

Final comparison

Native

cert-manager
      ↓
Venafi Issuer
      ↓
Venafi

Best when:

  • the Kubernetes Secret is persistent
  • each certificate is managed independently
  • the platform controls certificate lifecycle
  • cross-cluster certificate sharing is handled outside cert-manager

Custom external issuer

cert-manager
      ↓
CertificateRequest
      ↓
Custom Venafi Issuer
      ↓
lookup existing certificate
      ↓
reuse OR issue
      ↓
Venafi

Best when the explicit requirement is:

Check Venafi for an existing certificate before requesting a new one.

The custom issuer is an extension around cert-manager; cert-manager itself does not need to be forked or modified.
